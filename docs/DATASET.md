# Данные заказчика: что используется и как

Файлы заказчика лежат в `data/organizers/` и в репозиторий не попадают. Всё, что из них получено
программно, лежит в `data/seed/` и входит в поставку: система поднимается и без файлов заказчика.
Импорт в базу: `docker compose exec backend python -m app.importers.organizers` (повторный запуск
ничего не дублирует; если рядом лежит xlsx классификатора, `seed/classifier.json` пересобирается).

| Файл заказчика | Что внутри | Как используется |
|---|---|---|
| `Классификатор_происшествий_v046.xlsx` | 1310 строк × 99 колонок, лист «Лист1» | импортируется: `incident_groups`, `incident_types`, `incident_flags`, `services`; `seed/classifier.json` |
| `Классификатор_происшествий_v_046_11_ДТУ_15_11_2024.xlsx` | 1308 строк × 90 колонок, 1281 тип, есть колонка «Сценарий реагирования» | не импортируется, сверен с v046 (раздел 1) |

## 1. Классификатор происшествий (xlsx)

### Какая версия

Программа работает по `Классификатор_происшествий_v046.xlsx`: **24 группы, 1283 итоговых типа,
64 службы, 16 признаков** (`data/seed/classifier.json`). Версию v_046_11 от 15.11.2024
сверили построчно по кодам типов:

- в v_046_11 нет двух типов v046: `23.6.0.1` «Прочие происшествия (от 102)» и `24.12.2.0` «БВС
  Регион», новых типов нет;
- у одного типа другое написание: «Запах бытового газа в метро (тонелле)» вместо «(тоннеле)»;
- колонка M «Сценарий реагирования» — новая. Заказчик пояснил, что это технические коды для
  опросных карт оператора 112, а для диспетчеров ДДС сценария нет. Набор служб по типу
  программа и так берёт из колонок служб, поэтому эта колонка не нужна.

Переход на v_046_11 ничего не меняет в оценке ДДС, поэтому импортируется v046.

### Структура

Лист «Лист1», 99 заполненных колонок (A–CU). Строки 1–3 — шапка с объединёнными ячейками, данные
с 4-й строки, всего 1307 строк данных.

| Колонки | Содержимое | Куда |
|---|---|---|
| A–D | коды `Г`, `п1`, `п2`, `п3` | код типа `Г.п1.п2.п3`, например `1.1.1.1` |
| E | формула номера (`Г·10⁶ + п1·10⁴ + п2·10² + п3`); у строк-заголовков групп — порядковый номер группы | не используется (код собирается из A–D) |
| F | у строки-заголовка группы — название группы; у строк типов — подгруппа «учёт в статистике», заполнена на первой строке подгруппы | `incident_groups.title`; `incident_types.stat_group` (протягивается вниз) |
| G, H, I | 112-Признак.1 / .2 / .3 — кнопки опросной карты | `sign1`, `sign2`, `sign3` |
| J | дополнительные признаки, не влияющие на тип (подсказки оператору: «В: кто сообщает…», «Нет доступа», «Применяется оружие») | `hints` |
| K | итоговый тип происшествия | `final_title` (уникален, 1283 значения) |
| L | тип ЕКП 35 | `ekp_title` (у 36 строк пусто, у ~60 «Нет в ЕКП») |
| M | главная служба (`MCHS`, `Police`, `AMBULANCE`, …, 27 вариантов; у 102 строк пусто, у 3 через запятую) | `main_service` (первый код), `main_service_raw` |
| N–CU | 86 колонок служб | `service_rules` |

Как строки различаются: строка с пустой K и заполненной F — заголовок группы (их 24); строка с
заполненной K — итоговый тип (их 1283, дублей кодов нет).

Группы (24): 23 пронумерованных в E и «БПЛА» без номера в самом конце (получила номер 24).

Заполнение признаков у типов: только G — 308 строк; G+H — 582; G+H+I — 387; G+I без H — 6
(эти шесть в дереве опросной карты идут как G → I).

144 типа с кодом `1.99.*` («Не отображается оператору 112») в дерево опросной карты оператора
не попадают, но остаются в базе: по ним подбираются службы и считается оценка.

### Шапка колонок служб (N–CU)

Строка 1 — семейство (служба или ведомство), строка 2 — подслужба или условие, строка 3 —
условие по дополнительному признаку. Разбор программный (`backend/app/importers/classifier.py`):
объединённые ячейки разворачиваются, тексты нормализуются, затем `(семейство, подслужба)` → код
службы, текст условия → код признака. Все 86 колонок разобраны, неразобранных нет.

Службы с подколонками по признакам:

| Служба | Колонки | Условия → признак |
|---|---|---|
| Служба 101 | N, O | НД не выбран → без признака; выбран НД → `no_access` |
| ОДС ПСЦ | P–S | другие не выбраны; УЛ → `threat`; ПП → `injured`; НД → `no_access` |
| Классификатор МВД (102) | U–W | не выбран; Правонарушение → `offense`; Пострадавшие → `injured` |
| Классификатор СМП (103) | X–Z | не выбран; Пострадавшие → `injured`; Пострадавшие не на месте → `not_on_site` |
| Мосгаз | AA, AB | не выбран; газификация → `gasification` |
| ЦЭМП | AC–AG | не выбраны; угроза людям → `threat`; пострадавшие/погибшие → `injured`; мед. помощь → `medical_help`; треб. эвакуация → `evacuation` |
| ФСБ | AH, AI | не выбран; >5 чел / ОД → `mass_incident` |
| Мосгортранс | AL–AN | не выбран; постр / погибшие → `injured`; перекрытие движение → `road_closed` |
| Гормост | AP–AS | не выбран; тоннель → `tunnel`; пеш → `pedestrian_bridge`; ав → `road_bridge` |
| МГТС | AU, AV | реагирование всегда → без признака; на объектах связи → `telecom_object` |
| Департамент строительства | BZ, CA | не выбран; стройка → `construction_site` |
| Департамент культуры | CD | единственная колонка «объект из перечня» → `listed_object` |
| ГКУ Организатор перевозок | CO, CP | не выбран; перекрытие движение → `road_closed` |

Подслужбы (две колонки одного ведомства, оба варианта заведены отдельными службами):
Департамент РБиПК (ГКУ МОСБЕЗ) → `duty_arm112` («Дежурная служба АРМ-112») и `mkp_analytics`;
ГУП МСР → `msr_kub` и `msr_fires`; ДГП → `dgp_integration` и `dgp_arm112`; Минобороны РХБЗ →
`mo_rhbz_polygons` и `mo_rhbz_moscow`. Остальные 40 семейств — одна колонка, одна служба.

Итого 64 службы и 16 признаков. Полный список кодов — в `classifier.py` (`SERVICE_COLUMNS`,
`FLAGS`), в базе — `services` и `incident_flags`.

### Значения ячеек

Ячейка заполнена — служба в списке оповещения. Значение — это название типа в классификаторе
самой службы («пожар», «Травма», «ДТП без пострадавших») либо «карточка-112» (службе уходит
карточка как есть; встречается в трёх написаниях: `карточка-112`, `Карточка-112`,
`карточка -112`). Формулы вида `=K5` (колонка CI, ГУП МСР пожары) повторяют итоговый тип строки и
раскрываются при импорте. Значение `нет реагирования` (741 ячейка, все в колонке Z — СМП при
признаке «пострадавшие не на месте») означает обратное: при этом признаке служба **не**
оповещается.

### Правила служб (`service_rules`)

На каждую заполненную ячейку строки — одно правило:

```json
{"service": "103", "when": ["injured"], "notify": true, "value": "Травма"}
{"service": "103", "when": ["not_on_site"], "notify": false, "value": "нет реагирования"}
```

`resolve_services(rules, flags)` (`backend/app/domain/services.py`): применяются правила, все
признаки которых выбраны (пустой `when` — всегда); результат — объединение положительных минус
службы отрицательных. Колонки «признак не выбран» действуют всегда, колонки с признаком добавляют
службу при выборе признака. Проверка: `backend/tests/test_resolve_services.py` сверяет результат с
сырыми ячейками xlsx по независимой карте колонок — на 30 выбранных строках с признаками и на всех
1283 строках без признаков.

Почему объединение, а не «колонка признака вместо колонки по умолчанию»: у 259 типов колонка 101
заполнена, а «101 при НД» и обе колонки ОДС ПСЦ пусты — при исключающей трактовке пожар с
признаком «нет доступа» остался бы без пожарных. В таблице колонки признаков заполнены только
там, где признак имеет смысл (например «НД» у 114 типов вроде «открыть дверь»).

`incident_types.flag_codes` — признаки, которые меняют список оповещения этого типа (их и надо
показывать в опросной карте).

### Где классификатор работает в программе

- **Карточка ДДС.** Полоса служб внизу карточки — это список оповещения типа с учётом признаков.
  Своя служба обучаемого — одна из них; остальные видны только для чтения, им можно позвонить.
- **Сложность карточек ИИ** (`backend/app/domain/scenarios/ai_plan.py`). Группы классификатора
  разделены на бытовые и ЧС: на сложности 1 — бытовые группы и 1–4 службы в списке оповещения, на
  2 — бытовые посложнее и 4–12 служб, на 3 — ЧС (пожары, взрывы, обрушения, природные и
  техногенные аварии) и от 10 служб. Карточку получает ДДС одной из пяти служб с аварийной бригадой:
  Городское хозяйство (ЕДЦ ЖКХ), Мосгаз, Мосводоканал, МОЭК, Гормост; берутся только типы, о которых
  классификатор оповещает эту службу.
- **Ошибка «не та служба»**: карточку отправляют в службу, которой тип не касается, — верный ответ
  «Не принята: не в компетенции службы».
- **Ошибка «соседний тип»**: в карточке другой итоговый тип той же ветки классификатора.
- **Оператор 112**: опросная карта строится по признакам G–I, службы подбираются правилами.
- **Справочник обучаемого**: классификатор с поиском по словам.

`data/seed/type_synonyms.json` (наш файл, выгрузка заказчика не меняется) — как заявитель
называет происшествие для 42 типов («лицо перекошено, речь невнятная» → инсульт). Эти слова
добавляются к тексту типа при поиске: и когда система подбирает тип для генерации, и когда
обучаемый ищет тип в карточке.

### Что не разобрано и особенности

- Колонка J (подсказки) хранится текстом как есть; в кнопки не превращается.
- Колонка L: 36 пустых и ~60 вариантов «Нет в ЕКП» в разном регистре — хранятся как есть.
- Колонка M: значение `' '` (пробел) у одной строки считается пустым; `METRO, MZD` и
  `MOESK, OEK` — берётся первый код, сырой текст сохраняется.
- Опечатки в исходных названиях («ДТП без пострадаших», «Брошеная автомашина», «Депортамент») не
  исправляются: датасет главнее.
- `services.via_arm112` — все службы, кроме интегрированных по памятке (стр. 7): 101, 102, 103,
  ЦОДД, Мосводоканал и ДГП «интеграция». Служба 104 в классификаторе не встречается.
- `services.no_reject` — только 103 (памятка, стр. 23): у неё нет «Не принята» и «Отказа от
  выполнения работ».

## 2. Билеты (PDF-скан)

32 страницы, у каждой в PDF стоит `/Rotate 180`, поэтому при рендере страницы уже перевёрнуты
правильно. На странице «БИЛЕТ N», подзаголовок и таблица «№ | Ситуация | Адрес» из трёх строк; у
нескольких билетов таблица упирается в нижний край страницы и нижняя линия обрезана.

Распознавание (`backend/app/importers/tickets_ocr.py`, Tesseract 5, язык `rus`, 300 dpi): сетка
таблицы ищется по проекциям тёмных пикселей (4 вертикали, 5 горизонталей; при обрезанной нижней
линии низ берётся по концу вертикалей), каждая ячейка распознаётся отдельно (`--psm 6`), поэтому
колонки не перемешиваются. Номер билета читается из заголовка над таблицей.

Результат `data/seed/tickets.json`: 96 ситуаций (32 × 3), поля `ticket_no`, `item_no`,
`situation`, `address`, `ocr_confident`, `confidence` (средняя уверенность Tesseract по словам
ячейки, минимум из двух колонок). Строка считается неуверенной при уверенности ниже 80 % или при
подозрительных символах (`[ ] \ { } | # @ $ ^ * _ ~ < >` и латиница из двух и более букв).

Ручная сверка: все 96 строк сверены с изображениями сканов в два прохода (второй проход
16.09.2026 постранично нашёл ещё 13 ошибок, пропущенных первым). Ошибки OCR исправлены через
`data/seed/tickets_corrections.json` (47 правок, применяются после распознавания, поэтому запуск
воспроизводим):
- «ири» → «при» (курсив в скобках), «кори.» → «корп.», «болышая» → «большая»;
- «стр.Г» → «стр.1», «(МЗ)/(МТ)» → «(М3)/(М1)», «под. [» → «под. 1»;
- сокращения в ситуациях ДТП: «БТ Б/Р», «БЛЬ БР», «БАТ, Б/Р» → «Б/П, Б/Р» (без пострадавших,
  без разбора);
- билет 18 №3: в скане «дом 15/19» зачёркнуто и от руки написано «12» — взято «дом 12»;
- билет 21 №3: название ресторана «WHEITE» латиницей — есть в оригинале, строка подтверждена;
- билет 1 №1: низкая уверенность (73,7 %) из-за курсивного адреса, текст сверен и подтверждён;
- второй проход: «дом 115» → «дом 11Б» (билет 22 №3), потерянный «1 км» (билет 6 №1),
  «АЗС НЕМ» → «АЗС SHELL» (билет 12 №3, латиница подтверждена), «КИТ» → «КПП» (билет 20 №2),
  «7 128 7? 177» → «? 128 ?? 177» (билет 31 №2: заявитель не разглядел буквы номера),
  «код ЭВ» → «код 5В», «корн.» → «корп.», «пт.» → «ш.», лишнее тире и склеенные/лишние пробелы;
- билет 15 №3: «Зверенецкая» → «Зверинецкая» (в Москве есть только Зверинецкая улица).

После правок неуверенных строк 0. Опечатки, которые есть в самих билетах («Домодедлво»,
«Молсыркомбината», «Сильная головная»), оставлены.

Ловушки (`tickets.traps`) вычисляются эвристикой при импорте
(`app/importers/organizers.py`, `TRAP_PATTERNS`): `other_region`, `descriptive_address`,
`call_dropped`, `injured`, `child`, `caller_not_victim`, `no_ambulance`, `entrance_details`. Это
подсказка преподавателю при генерации сценариев, не эталон.

### Как используются билеты

Заказчик дал 96 ситуаций, готовых сценариев в датасете нет. Из ситуаций сделано:

- **96 сценариев «Приём вызова»** — по одному на каждую ситуацию (`data/seed/scenarios/call_*.json`,
  раздел 5);
- **6 сценариев карточки ДДС** по билетам 2-1 (ещё повторный вызов к нему), 5-2, 17-1, 30-3, 31-3;
- **подсказка модели**: при написании любой карточки (генерация по фразе, под занятие, в режиме
  «Задания формирует ИИ») в запрос к модели попадают похожие ситуации из билетов, найденные по
  смыслу (`backend/app/providers/rag.py`);
- **адрес и заявитель из билета**: если карточка пишется по билету, адрес, ФИО и телефон берутся из
  билета, а не придумываются моделью (`providers/generation.py`, `_card_address`, `_card_caller`);
  голос заявителя подбирается по полу из ФИО (`scenarios/facts.py`, `caller_gender`);
- массовая генерация по всем билетам: `python -m app.scripts.generate_from_tickets --all`.

## 3. Памятка «Работа на АРМ-112»

Текстовый слой есть, OCR не нужен. `data/seed/memo.txt` — текст по страницам с маркерами
`===== Страница N =====` (`app/importers/memo_extract.py`). Что взято в справочники
(`backend/app/domain/reference_data.py`):

| Справочник | Страницы памятки | Записей |
|---|---|---|
| Статусы реагирования (`response_statuses`) | 21–23, порядок выбора — 25 | 9: Добавлена, Получена службой, Принята, Не принята, Начало реагирования, Прибытие, Проведение работ, Работы завершены, Отказ от выполнения работ |
| Статусы карточки (`card_statuses`) | 27–28 | 7, красная индикация у «Не оповещено», «Отказ», «Не завершено» |
| Причины отказа (`reject_reasons`) | 21, 28–30 (формулировки из примеров) | 7 |
| Типичные ошибки (`typical_errors`) | 18–19, 21–22, 26, 28–32 | 29: 24 для карточки ДДС и 5 для приёма вызова |
| Темы разговора заявителя (`caller_topics`) | — | 14, с ключевыми словами |

**Типичные ошибки — это правила оценки.** Каждое правило — отдельная функция
(`backend/app/domain/evaluation/detectors.py`) со штрафом, примером и ссылкой на страницу памятки;
в разборе ошибка показывается словами памятки. 11 правил карточки ДДС взяты из примеров памятки
(стр. 21–32: нет статуса, первичный статус позже норматива, статус не соответствует
реагированию, отказы по компетенции и от профильного происшествия, отказ без комментария,
неполный комментарий, нет статусов хода работ, «Принята» вместо «Не принята: дубль», ошибочная
«Принята» не исправлена, «Работы завершены» вместо отказа). Ещё 13 добавлены для заданий ДДС, которых
в памятке нет: пропущенная или ложно отмеченная ошибка оператора 112, служба не оповещена по
телефону или ей ничего не передали, статус хода работ раньше доклада бригады, доклад не отражён
статусом или не принят, не исправлено неверно понятое (сейчас не срабатывает: собеседник
дом не путает), не передано осложнение, не доложено
руководителю об отсутствии машин, не дано распоряжение на выезд, позвонил не тому, бригаде
передан неверный адрес. У трёх из них есть ссылка на памятку (стр. 22, 26, 31).

**Переходы статусов** (`allowed_next`) — по одному шагу, как в живом АРМ-112 на скриншотах
заказчика: сначала «Принята» или «Не принята»; после «Не принята» — только «Принята»; после
«Принята» — «Начало реагирования», «Работы завершены» или «Отказ от выполнения работ»; после
«Начала реагирования» — «Прибытие», после «Прибытия» — «Проведение работ», и на каждом шаге
можно закрыть карточку «Работами завершены» или «Отказом». Памятка (стр. 25) после «Принята»
открывает все статусы сразу; расхождение решено в пользу живой системы.

**Обязательные поля.** Комментарий — у «Не принята», «Работы завершены», «Отказ от выполнения
работ» (стр. 22) и у статусов хода работ «Начало реагирования», «Прибытие», «Проведение работ»
(стр. 31, пример 6: статусы «и комментарии к ним»). Номер наряда — у «Начала реагирования».
Служба 103 не отказывает: вместо «Отказа» — «Работы завершены» с комментарием «завершение работ
без бригады» (стр. 23).

**Где ещё работает памятка:**
- справочник обучаемого: полнотекстовый поиск по памятке с номером страницы
  (`backend/app/domain/memo_search.py`);
- советы после карточки ссылаются на страницу памятки
  (`backend/app/domain/evaluation/advice.py`);
- при написании карточки модель получает подходящие по смыслу фрагменты памятки
  (`providers/rag.py`).

Скриншоты интерфейса для эмулятора: `docs/reference/arm112/` — страницы 12 (главный экран), 13
(две карточки в журнале), 15 (карточка в процессе заполнения), 16 (сохранённая карточка), 17
(блоки карточки), 23 (вид карточки на АРМ-112 ДДС), 24 (проставление статуса). Колонки журнала,
строка статуса службы и полоса служб карточки ДДС сверены со скриншотами рабочего места ДДС
(`СКРИНШОТ_ДДС.docx`); подробности — в [DECISIONS.md](DECISIONS.md).

## 4. Улицы Москвы

Источник: OpenStreetMap через Overpass API (© участники OpenStreetMap, ODbL 1.0, см.
[LIBRARIES.md](LIBRARIES.md)). Скрипт `app/importers/streets_osm.py`: округа Москвы
(`admin_level=5`) → районы и поселения внутри (`admin_level=8`) → именованные улицы внутри района
(типы highway от `motorway` до `living_street`/`pedestrian`; служебные проезды и тропинки не
берутся). Улица, проходящая через несколько районов, встречается по разу на район. Результат —
`data/seed/streets.json` (6249 записей), в базе — `streets` с `name_normalized` (нижний регистр,
«ё» → «е») для подсказки `GET /streets?q=` по началу любого слова названия.

`data/seed/streets_manual.json` — две улицы из билетов, которых нет в выгрузке OSM (улица Красной
Сосны, Бережковский мост); добавлены вручную с источником `manual`.

Где используются: подсказка адреса в карточке оператора 112, настоящий адрес для карточки,
написанной по фразе (у неё нет адреса из билета), и ошибка «похожая улица» в карточке ДДС.

## 5. Учебные сценарии в поставке

`data/seed/scenarios/` — 114 сценариев, при первом запуске загружаются в базу утверждёнными
(`backend/app/seed.py`).

| Режим | Файлы | Всего | По сложности 1 / 2 / 3 |
|---|---|---|---|
| Приём вызова (оператор 112) | `call_*.json` | 96 — по одному на каждую ситуацию билетов | 11 / 37 / 48 |
| Реагирование на карточку (ДДС) | `card_*.json` | 18 | 6 / 8 / 4 |

Карточки ДДС:
- 6 по билетам (2-1 и повторный вызов к нему, 5-2, 17-1, 30-3, 31-3);
- 12 своих для служб с аварийной бригадой: ЖКХ (4), МОЭК (2), Мосводоканал (2), Гормост (1) и три
  карточки с заложенной ошибкой оператора 112 (раздел 6);
- у 13 карточек в эталоне есть звонок в свою службу и четыре доклада бригады (выехали, прибыли,
  приступили, завершили).

Сценарии поставки — это и образец для модели: при генерации в запрос кладётся один сценарий того
же режима, по возможности той же ветки классификатора (`backend/app/domain/scenarios/examples.py`).

**Карточки, которые пишет ИИ.** В режиме «Задания формирует ИИ» сценарии не берутся из библиотеки:
каждому обучаемому карточка пишется во время занятия (`backend/app/training/ai_cards.py`). Модель
получает тип из классификатора, подобранный под ошибки обучаемого (`ai_plan.py`), похожие билеты,
фрагменты памятки, образец сценария и список настоящих улиц. Если модель не ответила, карточка
собирается по шаблону. Такие карточки принадлежат своему занятию и в библиотеку не попадают.

## 6. Заложенные ошибки оператора 112

Заказчик уточнил: диспетчер ДДС получает карточку уже заполненной и проверяет её на ошибки.
Поэтому часть карточек ДДС несёт `injected_errors`: поле карточки показывает неверное значение, а
верное записано в сценарии и названо в описании со слов заявителя.

Сколько ошибок, зависит от сложности: на 1 — ни одной, на 2 — ровно одна, на 3 — ровно две
(`backend/app/domain/scenarios/distort.py`, `MISTAKES_BY_DIFFICULTY`). Каждая ошибка видна:
если описание ещё не называет правду, к нему добавляется фраза вроде «Заявитель уточнил, что
пострадавших нет». Выбор ошибки повторяется при перегенерации того же сценария. В режиме
«Задания формирует ИИ» первыми закладываются ошибки того вида, который обучаемый уже пропускал.

| Вид ошибки | Как искажается | Что должен сделать диспетчер |
|---|---|---|
| `address.house` | соседний номер дома (±1, ±2) | отметить поле, ввести верный дом, бригаде назвать верный |
| `address.street` | похожая улица из справочника (сходство 60–92 %) | отметить и исправить |
| `incident_type` | соседний тип той же ветки классификатора | отметить и исправить |
| `flags.injured` | «Пострадавшие» вопреки описанию | отметить и исправить |
| `service` | карточка отправлена в службу, которой тип не касается | «Не принята» с причиной «Не в компетенции службы» |

В одной карточке не бывает двух ошибок адреса сразу. В режиме «Задания формирует ИИ» «не той
службе» приходит третья карточка занятия (на практике — в вале сложности 3), и такая ошибка
повторяется в следующей карточке, если обучаемый её пропустил; она считается одной из ошибок
карточки.

В поставке три готовые карточки с ошибкой (`data/seed/scenarios/card_err_*.json`, сложность 3, по
одной ошибке): явная («Пострадавшие: да» при «Пострадавших нет» в описании, ЖКХ), тонкая (дом 19
вместо 17, МОЭК) и «служба лишняя» (Мослифт в списке оповещения при прорыве водопровода,
Мосводоканал).

## 7. Звонки и собеседники ДДС

Заказчик: «в рамках телефонии фокус на взаимодействии Б (диспетчер ДДС) и В (службы)»; в
рекомендациях к финалу — виртуальный телефон с четырьмя собеседниками и номерами от
преподавателя.

- **Эталон звонков** (`reference.service_calls`): кому позвонить и какие факты передать (из
  `address`, `incident_type`, `injured`, `order_number`, `access`), норматив звонка 120 с. В файлах
  поставки он записан у 13 карточек ДДС. Принятой карточке без записанного эталона, в том числе
  карточке ИИ, он подставляется сам (`officers.py`, `default_service_calls`): звонок в свою службу
  с адресом, типом происшествия и пострадавшими, плюс доступ, если в карточке есть код или «нет
  доступа». Номер наряда называет бригада, диспетчер его записывает. Так же подставляется шкала
  докладов бригады.
- **Справочник телефонов** (`backend/app/training/phones.py`): у каждой службы до 10 номеров, по
  умолчанию четыре роли из рекомендаций заказчика — руководитель организации, начальник отдела
  реагирования, начальник аварийной бригады, специалист аварийной бригады — с номерами вида 21xx.
  Преподаватель правит справочник; обучаемый видит справочник своей службы. Строка «Заявитель —
  номер из карточки» появляется, только если звонок заявителю разрешён в занятии.
- **Кто отвечает**: трубка на вкладке своей службы — начальник аварийной бригады, на вкладках
  других служб — их дежурные (`backend/app/domain/scenarios/officers.py`, `staff.py`). Бригада сама
  звонит с докладами по шкале эталона (`reference.reports`).
- **Поведение по сложности**: на 3 собеседники торопят, у бригады бывает осложнение на месте
  (нужна ещё одна служба) или «машин нет» (надо доложить руководителю).
