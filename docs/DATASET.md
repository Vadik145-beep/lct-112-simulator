## 1. Классификатор происшествий (xlsx)

### Структура

Лист «Лист1», 99 колонок (в PRD было сказано 104, фактически 99: A–CU). Строки 1–3 — шапка
с объединёнными ячейками, данные с 4-й строки, всего 1307 строк данных.

| Колонки | Содержимое | Куда |
|---|---|---|
| A–D | коды `Г`, `п1`, `п2`, `п3` | код типа `Г.п1.п2.п3`, например `1.1.1.1` |
| E | формула номера (`Г·10⁶ + п1·10⁴ + п2·10² + п3`); у строк-заголовков групп — порядковый номер группы | не используется (код собирается из A–D) |
| F | у строки-заголовка группы — название группы; у строк типов — подгруппа «учёт в статистике», заполнена на первой строке подгруппы | `incident_groups.title`; `incident_types.stat_group` (протягивается вниз) |
| G, H, I | 112-Признак.1 / .2 / .3 — кнопки опросной карты | `sign1`, `sign2`, `sign3` |
| J | дополнительные признаки, не влияющие на тип (подсказки оператору: «В: кто сообщает…», «Нет доступа», «Применяется оружие») | `hints` |
| K | итоговый тип происшествия | `final_title` (уникален, 1283 значения) |
| L | тип ЕКП 35 | `ekp_title` (у 36 строк пусто, у ~60 «Нет в ЕКП») |
| M | главная служба (`MCHS`, `Police`, `AMBULANCE`, …, 27 вариантов; у 102 строк пусто, у 3 через запятую) | `main_service` (первый код), `main_service_raw` |
| N–CU | 86 колонок служб | `service_rules` |

Как строки различаются: строка с пустой K и заполненной F — заголовок группы (их 24);
строка с заполненной K — итоговый тип (их 1283, дублей кодов нет). Итого 1283 типа, PRD
называл «около 1284».

Группы (24): 23 пронумерованных в E и «БПЛА» без номера в самом конце (получила номер 24).

Заполнение признаков у типов: только G — 308 строк; G+H — 582; G+H+I — 387; G+I без H — 6
(эти шесть в дереве опросной карты идут как G → I).

### Шапка колонок служб (N–CU)

Строка 1 — семейство (служба или ведомство), строка 2 — подслужба или условие,
строка 3 — условие по дополнительному признаку. Разбор программный
(`backend/app/importers/classifier.py`): объединённые ячейки разворачиваются, тексты
нормализуются, затем `(семейство, подслужба)` → код службы, текст условия → код признака.
Все 86 колонок разобраны, неразобранных нет.

Итого 64 службы и 16 признаков. Полный список кодов — в `classifier.py`
(`SERVICE_COLUMNS`, `FLAGS`), в базе — `services` и `incident_flags`.

### Значения ячеек

Ячейка заполнена — служба в списке оповещения. Значение — это название типа в
классификаторе самой службы («пожар», «Травма», «ДТП без пострадавших») либо «карточка-112»
(службе уходит карточка как есть; встречается в трёх написаниях: `карточка-112`,
`Карточка-112`, `карточка -112`). Формулы вида `=K5` (колонка CI, ГУП МСР пожары) повторяют
итоговый тип строки и раскрываются при импорте. Значение `нет реагирования` (741 ячейка, все в
колонке Z — СМП при признаке «пострадавшие не на месте») означает обратное: при этом признаке
служба **не** оповещается.

### Правила служб (`service_rules`)

На каждую заполненную ячейку строки — одно правило:

```json
{"service": "103", "when": ["injured"], "notify": true, "value": "Травма"}
{"service": "103", "when": ["not_on_site"], "notify": false, "value": "нет реагирования"}
```

`resolve_services(rules, flags)` (`backend/app/domain/services.py`): применяются правила, все
признаки которых выбраны (пустой `when` — всегда); результат — объединение положительных минус
службы отрицательных. Колонки «признак не выбран» действуют всегда, колонки с признаком добавляют
службу при выборе признака. Проверка: `backend/tests/test_resolve_services.py` сверяет результат
с сырыми ячейками xlsx по независимой карте колонок — на 30 выбранных строках с признаками и на
всех 1283 строках без признаков.

Почему объединение, а не «колонка признака вместо колонки по умолчанию»: у 259 типов колонка
101 заполнена, а «101 при НД» и обе колонки ОДС ПСЦ пусты — при исключающей трактовке пожар
с признаком «нет доступа» остался бы без пожарных. В таблице колонки признаков заполнены только
там, где признак имеет смысл (например «НД» у 114 типов вроде «открыть дверь»).

`incident_types.flag_codes` — признаки, которые меняют список оповещения этого типа (их и надо
показывать в опросной карте).

### Что не разобрано и особенности

- Колонка J (подсказки) хранится текстом как есть; в кнопки не превращается.
- Колонка L: 36 пустых и ~60 вариантов «Нет в ЕКП» в разном регистре — хранятся как есть.
- Колонка M: значение `' '` (пробел) у одной строки считается пустым; `METRO, MZD` и
  `MOESK, OEK` — берётся первый код, сырой текст сохраняется.
- Опечатки в исходных названиях («ДТП без пострадаших», «Брошеная автомашина», «Депортамент»)
  не исправляются: датасет главнее.
- `services.via_arm112` — все службы, кроме интегрированных по памятке (стр. 7): 101, 102, 103,
  ЦОДД, Мосводоканал и ДГП «интеграция». Служба 104 в классификаторе не встречается.
- `services.no_reject` — только 103 (памятка, стр. 23).

## 2. Билеты (PDF-скан)

32 страницы, у каждой в PDF стоит `/Rotate 180`, поэтому при рендере страницы уже
перевёрнуты правильно. На странице «БИЛЕТ N», подзаголовок и таблица «№ | Ситуация | Адрес» из
трёх строк; у нескольких билетов таблица упирается в нижний край страницы и нижняя линия
обрезана.

Распознавание (`backend/app/importers/tickets_ocr.py`, Tesseract 5, язык `rus`, 300 dpi):
сетка таблицы ищется по проекциям тёмных пикселей (4 вертикали, 5 горизонталей; при обрезанной
нижней линии низ берётся по концу вертикалей), каждая ячейка распознаётся отдельно (`--psm 6`),
поэтому колонки не перемешиваются. Номер билета читается из заголовка над таблицей.

Результат `data/seed/tickets.json`: 96 ситуаций (32 × 3), поля `ticket_no`, `item_no`,
`situation`, `address`, `ocr_confident`, `confidence` (средняя уверенность Tesseract по словам
ячейки, минимум из двух колонок). Строка считается неуверенной при уверенности ниже 80 % или
при подозрительных символах (`[ ] \ { } | # @ $ ^ * _ ~ < >` и латиница из двух и более букв).

Ручная сверка: все 96 строк сверены с изображениями сканов в два прохода (второй проход
16.09.2026 постранично нашёл ещё 13 ошибок, пропущенных первым). Замеченные ошибки OCR
исправлены через `data/seed/tickets_corrections.json` (46 правок, применяются после
распознавания, поэтому запуск воспроизводим):
- «ири» → «при» (курсив в скобках), «кори.» → «корп.», «болышая» → «большая»;
- «стр.Г» → «стр.1», «(МЗ)/(МТ)» → «(М3)/(М1)», «под. [» → «под. 1»;
- сокращения в ситуациях ДТП: «БТ Б/Р», «БЛЬ БР», «БАТ, Б/Р» → «Б/П, Б/Р»
  (без пострадавших, без разбора);
- билет 18 №3: в скане «дом 15/19» зачёркнуто и от руки написано «12» — взято «дом 12»;
- билет 21 №3: название ресторана «WHEITE» латиницей — есть в оригинале, строка подтверждена;
- билет 1 №1: низкая уверенность (73,7 %) из-за курсивного адреса, текст сверен и подтверждён;
- второй проход: «дом 115» → «дом 11Б» (билет 22 №3), потерянный «1 км» (билет 6 №1),
  «АЗС НЕМ» → «АЗС SHELL» (билет 12 №3, латиница подтверждена), «КИТ» → «КПП» (билет 20 №2),
  «7 128 7? 177» → «? 128 ?? 177» (билет 31 №2: заявитель не разглядел буквы номера),
  «код ЭВ» → «код 5В», «корн.» → «корп.», «пт.» → «ш.», лишнее тире и склеенные/лишние пробелы.

После правок неуверенных строк 0 (порог плана — не больше 10). Опечатки, которые есть в самих
билетах («Домодедлво», «Молсыркомбината», «Сильная головная»), оставлены.

Ловушки (`tickets.traps`) вычисляются эвристикой при импорте
(`app/importers/organizers.py::detect_traps`): `other_region`, `descriptive_address`,
`call_dropped`, `injured`, `child`, `caller_not_victim`, `no_ambulance`, `entrance_details`.
Это подсказка преподавателю при генерации сценариев, не эталон.

## 4. Улицы Москвы

Источник: OpenStreetMap через Overpass API (© участники OpenStreetMap, ODbL 1.0, см.
`docs/LIBRARIES.md`). Скрипт `app/importers/streets_osm.py`: округа Москвы (`admin_level=5`) →
районы и поселения внутри (`admin_level=8`) → именованные улицы внутри района (типы highway от
`motorway` до `living_street`/`pedestrian`; служебные проезды и тропинки не берутся). Улица,
проходящая через несколько районов, встречается по разу на район. Результат —
`data/seed/streets.json`, в базе — `streets` с `name_normalized` (нижний регистр, «ё» → «е») для
подсказки `GET /streets?q=` по началу любого слова названия.

## Заложенные ошибки оператора 112 (задача #35)

Заказчик уточнил: диспетчер ДДС получает карточку уже заполненной и проверяет её на ошибки.
Часть сценариев `card_response` поэтому несёт `injected_errors`: карточка показывает неверное
значение, верное известно только сценарию.

| Поле | Как искажается | Заметность |
|---|---|---|
| `address.house` | соседний номер дома (±1, ±2) | 2 |
| `address.street` | похожая улица из справочника (`rapidfuzz` 60–92 %) | 3 |
| `incident_type` | соседний тип классификатора (та же группа, другой итоговый тип) | 2 |
| `flags.injured` | «Пострадавшие» вопреки описанию | 1 |
| `services` | лишняя оповещённая служба (`+код`) или недостающая (`-код`) | 1–2 |

Генератор (`app.domain.scenarios.distort`) добавляет ошибку по сложности сценария: 1 → нет,
2 → 30 %, 3 → 50 % (иногда две). Описание со слов заявителя всегда содержит верное значение.

В seed три готовые карточки (`data/seed/scenarios/card_err_*.json`): явная («Пострадавшие: да»
при «Пострадавших нет» в описании, ЖКХ), тонкая (дом 19 вместо 17, МОЭК) и «служба лишняя»
(Мослифт на прорыве водопровода, Мосводоканал). Все сложности 3.
