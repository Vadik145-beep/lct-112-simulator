# Проверка подсчёта оценки на живых звонках

Как мы проверяли, что балл на живом голосовом звонке считается правильно, и что изменилось в
оценке звонков после этой проверки.

| Что | Режим | Как проверено | Дата |
|---|---|---|---|
| 12 живых звонков с облачным заявителем, балл сверен с независимым пересчётом | «Приём вызова» (оператор 112) | набор `frontend/e2e/vapi`, раздел 1 | 21.09.2026 |
| Правила оценки звонков диспетчера ДДС, уточнённые после живых звонков на стенде | «Реагирование на карточку» (ДДС) | автотесты бэкенда на записанных случаях, раздел 3 | 17–19.10.2026 |

Живого прогона с независимым пересчётом для звонков ДДС нет: правила звонков ДДС проверяются
автотестами, раздел 3.

## 1. Набор живых звонков приёма вызова

Набор `frontend/e2e/vapi/` — двенадцать живых звонков против стенда с включённым облачным голосом
(`CLOUD_VOICE_ENABLED=true`, ключи Vapi). Проверяется режим «Приём вызова»: обучаемый в роли
оператора 112 принимает звонок и заполняет карточку. По рекомендации заказчика этот режим теперь
скрыт и включается администратором отдельным пользователям; основной режим тренажёра — ДДС.

В каждом звонке заявителя целиком играет Vapi (распознавание → модель → голос ElevenLabs), а
диспетчера — тест: вместо микрофона Chrome получает синтетический поток, в который подмешиваются
заранее озвученные реплики (`phrases/*.wav`, голос Windows «Irina»). Vapi слышит живую речь,
отвечает голосом, стенограмма приходит на сервер. После каждой реплики тест ждёт ответ
заявителя в стенограмме, затем заполняет карточку, завершает звонок, сохраняет и открывает
разбор.

Смысл набора — не «звонок проходит», а **подсчёт баллов**: после каждого звонка оценка из API
сверяется с независимым пересчётом (`lib/scoring.ts` — перенос формул движка
`backend/app/domain/evaluation/` на TypeScript): нормировка весов к 100, каждая составляющая по её
`items` (адрес по весам частей, службы по Жаккару, время по нормативу, грамотность по числу
замечаний, штрафы типичных ошибок), обязательные вопросы по ключевым словам из стенограммы,
итог = Σ баллов / Σ максимумов × 100, зачёт по порогу, совпадение балла на карточке, в разборе и в
API. Двенадцать случаев подобраны так, чтобы задеть каждую ветку правил (частичные баллы,
нормировка нестандартных весов, порог зачёта, линейный спад времени, пустой ввод, лишние
признаки).

## 2. Что изменилось в оценке приёма вызова после прогона

По коду `backend/app/domain/evaluation/call_intake.py` и `detectors.py`:

- **Обязательные вопросы в облачном звонке считаются только по словам обучаемого.** Заявитель
  Vapi говорит свободно, и темы по его словам засчитывали бы вопросы, которых не задавали. В
  звонке с локальной моделью ответ заявителя по-прежнему засчитывает тему вопроса, на который он
  отвечает.
- **Два блокирующих правила** — критические ошибки, при которых «незачёт» при любом балле:
  «Обязательные вопросы не заданы» (обучаемый сам задал меньше доли
  `min_questions_share` обязательных вопросов, по умолчанию половины) и «Карточка не заполнена»
  (нет ни типа, ни признаков, ни адреса, ни описания).
- **Пустой ввод даёт 0, а не максимум.** Описание короче двух слов — 0 за описание и за
  грамотность; пустая карточка — ещё 0 за признаки и службы и за время.
- **Норматив приёма вызова по умолчанию 60 с** вместо 90 (таймер живого АРМ-112). Набор задаёт
  норматив занятия явно (180 с), поэтому на нём это не сказывается.
- Перед сохранением карточки — подтверждение «Оповестить службы и сохранить»; тест нажимает его
  (`lib/flow.ts`).

Что это значит для набора:

- По правилам сейчас тесты 06, 08 и 11 должны давать «незачёт»: в 06 карточка пустая, в 08 и 11
  обучаемый сам задал меньше половины обязательных вопросов. Тест 06 ожидает незачёт, тесты 08 и
  11 зачёт не проверяют.
- Пересчёт `lib/scoring.ts` этих правил ещё не знает. Он считает темы по репликам обеих сторон,
  а грамотность, время и признаки пустой карточки — по сентябрьским формулам. Перед повторным
  прогоном его нужно довести до текущих правил, иначе тесты 06, 08 и 11 покажут расхождения, хотя
  движок считает правильно.

## 3. Звонки диспетчера ДДС: что проверяется сейчас

В режиме ДДС голосом идут звонки диспетчера: начальнику аварийной бригады своей службы,
дежурным других служб, руководителю организации и начальнику отдела реагирования. Бригада и
специалист звонят сами с докладами. Звонок ведёт локальная модель или облако (Vapi). Оценку
звонков считает составляющая «Звонки в службы» (`backend/app/domain/evaluation/service_call.py`,
вес 15) и правила типичных ошибок.

**Как считается звонок.**

| Звонок | Доли балла |
|---|---|
| Начальнику аварийной бригады своей службы | дозвонился до нужных людей 25 % (при «машин нет» нужен ещё руководитель организации), передал факты 30 %, исправил неверно понятый дом 15 %, дал распоряжение на выезд и записал номер наряда 15 %, уложился в норматив 15 % |
| Дежурному другой службы | дозвонился 30 %, передал факты 50 %, уложился в норматив 20 % |

Звонок, в котором не передан ни один обязательный факт, даёт 0: дозвониться и промолчать — то же,
что не звонить. Норматив звонка 120 с. Начальник бригады сейчас дом не путает (этот приём
отключён 18.10.2026), поэтому доля «исправил неверно понятый дом» засчитывается всегда, а правило
«Не исправлено неверно понятое» не срабатывает.

**Что изменилось в октябре** (так помечено в коде: живые звонки на стенде 17–19.10.2026):

- *Адрес засчитывается по правде карточки.* Если оператор 112 ошибся в доме, верным считается дом
  из описания со слов заявителя; назвать бригаде дом из поля — ошибка «Бригаде передан неверный
  адрес». Адрес узнаётся в любом падеже и порядке слов, с числительными словами, с улицей через
  дефис, по ключевому слову названия («Панфиловцев» для «Героев Панфиловцев»).
- *Тип происшествия* засчитывается, если диспетчер назвал его своими словами, которые есть в
  карточке, а не только по таблице ключевых слов.
- *Облачная анкета.* После облачного звонка начальнику бригады облако заполняет анкету из семи
  полей: назван ли адрес и какой дом, сказано ли что случилось, про пострадавших и доступ, дано ли
  распоряжение, исправлен ли дом. Факты этого звонка берутся из анкеты, а не из ключевых слов;
  дом из анкеты сверяется с правдой карточки на сервере. Без анкеты (локальная модель, другие
  собеседники) факты читаются из расшифровки.
- *Распоряжение.* Начальник бригады выезжает и называет наряд, как только узнал адрес и что
  случилось. Распоряжение диспетчер должен дать сам; оно узнаётся в обычных словах
  («выезжайте», «высылайте», «вы приедете?»). Нет распоряжения — ошибка «Не дано распоряжение на
  выезд» и потеря доли балла. На карточке «машин нет» распоряжение начальнику бригады не
  требуется.
- *Новые правила ошибок звонков:* «Позвонил не тому» (распоряжение руководителю организации),
  «Не доложено руководителю о нехватке сил», «Не оповещена служба об осложнении», «Дозвонились в
  службу, но ничего не передали».
- *Доклады бригады.* Сведения, которые бригада сообщила по телефону, считаются докладом; статус
  хода работ раньше доклада — ошибка, доклад без статуса — ошибка, не принятый звонок доклада —
  ошибка.
- *Решение.* Ошибочная «Принята», исправленная «Отказом от выполнения работ» с комментарием на
  карточке, которую следовало отклонить, засчитывается как исправление с потерей 6 баллов за
  «Принята»; цепочка и комментарий не обнуляются.
- *Комментарии.* Статусы хода работ сохраняются только с комментарием. Грамотность проверяется по
  каждому комментарию отдельно, с заглавной буквы: соседние комментарии больше не читаются как
  одно предложение.
- *Вал карточек* на сложности 3: баллы карточек не меняются, после вала отдельно показывается
  сводка — сколько пришло и закрыто, сколько с опозданием и без реакции, взята ли ЧС первой
  (`backend/app/training/stream.py`).

## 4. Как запустить набор живых звонков

Нужен стенд с облачным голосом и учётные записи преподавателя и обучаемого на нём. Обучаемый
должен состоять в группе преподавателя. Обоим администратор должен открыть режим оператора 112
(«Пользователи», галочка в колонке «Режим 112»): без неё преподаватель не создаст занятие приёма
вызова, а обучаемый его не увидит. Тест
завершает другие идущие занятия «Приём вызова», иначе софтфон возьмёт чужой звонок. Учётные данные
передаются только через окружение:

```bash
cd frontend
E2E_BASE_URL=https://<стенд> \
E2E_TEACHER_LOGIN=… E2E_TEACHER_PASSWORD=… \
E2E_STUDENT_LOGIN=… E2E_STUDENT_PASSWORD=… \
npx playwright test e2e/vapi
```

Около 40 минут на все двенадцать звонков (каждый — отдельное занятие, около 3 минут и кредиты
Vapi). `E2E_CASES=04,05` — выборочно, `E2E_HEADLESS=1` — без окна браузера. Без переменных
учётных записей набор пропускается, так что обычный `npm run e2e` его не запускает. Результаты в
`frontend/e2e/vapi/out/` (не в git): `suite-<час>.md` — строка на тест, `<час>-<тест>.json` —
стенограмма, оценка и все проверки, `<час>-<тест>.png` — экран после сохранения.

Файлы: `vapi-suite.spec.ts` — двенадцать случаев и ожидания; `lib/flow.ts` — занятие через API,
вход, звонок, реплики, варианты карточки; `lib/scoring.ts` — независимый пересчёт;
`lib/audio-bridge.js` — подмена `getUserMedia` синтетическим микрофоном; `phrases/` — реплики
диспетчера и `make-phrases.ps1` для их пересоздания (Windows, голос «Microsoft Irina»).
