# Правила проекта

Продукт описан в `PRD.md`, порядок работы в `plan/README.md`, текущее состояние в `docs/PROGRESS.md`.
Читать в этом порядке в начале каждой сессии.

## Задачи и ветки

Команда работает параллельно, поэтому порядок жёсткий.

1. **Каждая задача это issue** в этом репозитории. Без issue работу не начинать. Волна из `plan/`
   заведена как issue заранее; крупную волну можно разбить на несколько issue, каждая ссылается на
   файл волны.
2. **Взять задачу:** `gh issue view <N>`, прочитать целиком, затем `gh issue edit <N> --add-label in_progress`.
3. **Отдельный worktree и ветка от свежего `main`:**
   ```bash
   git fetch origin
   git worktree add ../lct-worktrees/<короткое-имя> -b wave-NN/<короткое-имя> origin/main
   ```
   Вся работа только внутри этого worktree. В основной папке клона код не менять.
4. Перед выводами о поведении кода убедиться, что дерево свежее: `git rev-list --count HEAD..origin/main`
   должно быть 0; иначе `git rebase origin/main`.
5. **Коммиты** на законченную подзадачу, по-русски, с номером issue: `feat: журнал ДДС и таймер принятия (#12)`.
   Перед коммитом `git status --short`; в коммит только относящиеся файлы (`git add -- <файлы>`).
6. **В `main` только через pull request:** `gh pr create --title "..." --body "Closes #N"`. Один PR
   закрывает одну issue. `push` в `main` напрямую запрещён.
7. **Конфликты** решает автор PR у себя в ветке (`git rebase origin/main`). Чужие ветки не трогать.
8. После мержа: `git worktree remove ../lct-worktrees/<имя>`, `git worktree prune`. Issue закрывается
   мержем.
9. Стенд и общие ресурсы (GPU-узел, телефония) занимаются с предупреждением в чате команды.

## Чистота репозитория

- **Нигде в коде, комментариях, коммитах, PR, документации и названиях файлов нет упоминаний
  ИИ-ассистентов, моделей и инструментов генерации кода.** Код читают эксперты заказчика.
  Подпись в коммитах отключена (`.claude/settings.json`), но правило шире подписи.
- Никаких секретов в git. Всё настраиваемое через `.env`; в `.env.example` безопасные значения.
- `data/organizers/` и `storage/` не коммитятся.
- Служебные файлы команды (`CLAUDE.md`, `.claude/`, `plan/PROMPTS.md`) вычищаются из истории перед
  публикацией репозитория (см. `plan/wave-12.md`).

## Код

- Код, имена и комментарии в коде на английском; интерфейс, сообщения об ошибках, документация и
  коммиты на русском.
- Никаких запросов во внешний интернет во время работы приложения, никаких CDN и внешних шрифтов.
  Исключение только `ALLOW_EXTERNAL_AI` для разработки (`PRD.md`, раздел 2).
- Без хардкода адресов, портов, путей и учётных данных вне настроек. Неизбежная константа именована,
  ограничена областью и описана.
- Новые зависимости только при реальной необходимости, с записью в `docs/LIBRARIES.md`.
- Тесты проверяют поведение, а не текст исходников. Читать файл проекта как строку и искать в нём
  подстроку запрещено. Лучше без теста, чем тест-заглушка.
- Не ослаблять и не отключать проверки ради зелёного результата.
- Текст кнопки говорит, что произойдёт; ошибка объясняет, что случилось и что сделать.
- Датасет заказчика (`data/organizers/`) главнее PRD: при расхождении прав датасет, решение в
  `docs/DECISIONS.md`.

## Ход работы

- Работать без остановок внутри волны. Спрашивать человека только если нужен секрет, доступ или
  платный ресурс; нужен выбор, которого нет в PRD и датасете и который меняет архитектуру или данные;
  проверки не зеленеют после трёх разных попыток. Тогда запись в `docs/BLOCKERS.md` и переход к
  независимой задаче.
- Самостоятельные решения по неясным местам одной-двумя строками в `docs/DECISIONS.md`.
- Не забегать в следующие волны.
- `docs/PROGRESS.md` ведётся так, чтобы новая сессия продолжила без контекста.
- PRD и план меняют только люди; предложения в `docs/DECISIONS.md`.
